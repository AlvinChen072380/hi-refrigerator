# 🐛 系統除錯與架構解惑筆記 (Cache & Git Post-mortem)

這份筆記記錄了在系統升級過程中，因為快取機制與 Git 協作所引發的經典複合型 Bug，以及關於前後端分離架構的核心觀念釐清。這對於未來維護大型專案非常有幫助。

---

## 🛑 經典除錯案例：「快取結構不相容」與「Git 覆寫」的複合型 Bug

### 💣 異常現象
部署完成後，點擊「全新的食譜」可以正常載入畫面；但是點擊「昨天測試過的舊食譜」，畫面卻會完全變成一片空白（Blank Screen）。

### 🔍 根本原因 (Root Causes)
這不是單一問題，而是由兩個常見坑點組合而成的複合型 Bug：

1. **Git 衝突覆寫 (The Git Overwrite)**
   為了避免讀到舊版格式的快取，開發者 A (AI) 在線上版加入了 `v2` 的快取命名空間 (`recipe:ai:v2:`)。
   同一時間，開發者 B (User) 在本地端進行了極好的程式碼優化（如加入 `enum`），但**尚未執行 `git pull`**，導致本地端的程式碼仍是舊的命名空間（無 `v2`）。
   當 B 將本地程式碼強制 `git commit` 並 Push 到線上時，**不小心把 A 寫的 `v2` 防護罩給覆寫抹除了**。

2. **快取資料結構不相容 (Cache Schema Incompatibility)**
   因為 `v2` 消失了，系統又去向 Redis 拿舊的快取資料。
   - **舊食譜（觸發 Cache Hit）**：Redis 給出舊版的龐大 JSON（包含 `title_zh`）。但我們最新的前端 `Adapter` 只認得新版的精簡變數（`title`）。Adapter 找不到 `title`，回傳了 `undefined`，導致 React 畫面渲染崩潰，變成一片空白。
   - **新食譜（觸發 Cache Miss）**：Redis 裡沒有這道菜的紀錄，系統乖乖去叫 Gemini 翻譯，Gemini 產出正確的新版精簡 JSON，Adapter 解析成功，畫面完美顯示！

### 💡 解決方案
在 `api/enrich-recipe.js` 中重新補回 `v2` 命名空間：
```javascript
const cacheKey = `recipe:ai:v2:${recipeData.idMeal}`;
```
這能「強制廢棄」所有舊快取，讓所有舊食譜在第一次點擊時都重新去向 AI 索取正確的新版格式，從此徹底解決結構不相容的問題。

## 🧠 架構解惑：後端封裝與快取生命週期

在開發與測試的過程中，我們透過 DevTool 觀察到了完美精簡的 JSON 回傳資料。以下是針對這個過程的架構釐清：

### ❓ 疑問一：快取的運作流程是「先查資料庫，有就直接顯示」嗎？
**✅ 正確！這就是 Cache Hit / Cache Miss 的標準生命週期。**
1. **Cache Miss (未命中)**：Vercel 伺服器發現 Redis 裡沒有這筆資料 ➔ 派 Gemini 去翻譯 ➔ 拿到精簡 JSON ➔ **先存進 Redis 資料庫** ➔ 回傳給瀏覽器。
2. **Cache Hit (命中)**：Vercel 伺服器一查 Redis，發現資料已經存在 ➔ **瞬間讀取，直接回傳給瀏覽器**。完全略過 Gemini 昂貴且耗時的翻譯過程。

### ❓ 疑問二：這段搜尋資料庫的過程都在伺服器內完成，本地端看不到嗎？
**✅ 正確！這稱為「後端封裝 (Backend Abstraction)」與「關注點分離 (Separation of Concerns)」。**
- 瀏覽器 (Frontend) 就像是去餐廳點餐的客人，它只負責送出「英文食譜 (點單)」，並期待收到「中文 JSON (餐點)」。
- 瀏覽器完全不需要知道這份 JSON 是花 5 秒鐘叫 Gemini 辛苦做出來的，還是花 0.05 秒從 Redis 冰箱拿出來的微波食品。
- 所有與 Redis 資料庫連線、驗證金鑰、執行的邏輯，全都隱藏在 Vercel 伺服器的記憶體中。這不僅讓前端程式碼更輕量，更保護了資料庫密碼的安全，是現代微服務架構的最佳實踐。
